## this session:
- Migrated frontend from plain HTML to React to support dynamic metrics polling
- Hooked React dashboard up to backend API; added VITE_API_URL environment handling for Vercel
- Debugged deployment timeout in CI: ServiceAccount missing from rbac.yaml, old pod wouldn't be replaced
- Implemented Prometheus querying instead of /proc parsing; realized container namespacing breaks host-level metrics
- Styled dashboard with industrial phosphor terminal aesthetic (Plex Mono, Bebas Neue, amber + cyan, CRT grain)

## why plain HTML → React
Started with a single static HTML/CSS/JS file—no framework, no build step, opens directly in a browser. For a read-only metrics dashboard with no routing or complex state, this was the right call initially. But the inflection point came immediately: the moment we needed to fetch data from the backend, poll it periodically, and re-render on updates, the constraints of vanilla JS became clear. React's component lifecycle and state management made the code cleaner and the polling logic easier to reason about. The build step (Vite) was worth it.

## frontend design
Used the frontend-design plugin to nail the aesthetic. Direction: industrial phosphor terminal meets mission control. 

**Typography:** IBM Plex Mono for code/metrics readability, Bebas Neue for headers to give it that command-center vibe.

**Color palette:** Amber (#e8a020) for critical/active states, cyan (#00d9b8) for secondary highlights, near-black (#080809) background. High contrast, low eye strain at a glance.

**Effects:** CRT grain texture via inline SVG `feTurbulence` filter baked into a data URI—keeps it snappy, no external textures. Dot grid background using CSS `repeating-linear-gradient`. SVG ring gauges animate using `stroke-dashoffset` (math: circumference ≈ 2π×44 ≈ 276.46px, dasharray equals circumference, offset animates from 0 to full to show percentage). Ticker loop is seamless by duplicating items and wrapping via animation keyframes. Page load staggered with `animation-delay` on each metric card for a slick entrance.

## deployment timeout issue in CI
GitHub Actions deploy step runs `kubectl rollout status deployment/k8s-platform --timeout=120s`. New pod never became ready. The culprit: ServiceAccount `k8s-platform` didn't exist because rbac.yaml was never applied to the cluster. k8s kept the old pod running (42h old at the time) and the new ReplicaSet had 0 desired replicas after a silent rollback.

**How we found it:** Ran `kubectl -n default get replicasets` and saw the new RS showing 0/0/0 (desired/current/ready). That's the giveaway—k8s created it but couldn't run it.

**Fix:** Applied rbac.yaml manually to unblock. Then added it to the CI deploy step before the deployment manifest apply. RBAC must exist before the deployment can reference it.

## VITE_API_URL and Vercel setup
React app uses `import.meta.env.VITE_API_URL` which defaults to `http://localhost:8080` for local dev. In production it must point to `https://api.lcpatterns.dev`. This is **not** a secret, but it is environment-specific, so it must be set as a Vercel environment variable (not in the repo).

**Vercel config:** Also had to set Root Directory to `frontend/dashboard` in the Vercel project settings so it knows where package.json lives and how to build.

## connecting kubectl to the VPS
k3s stores its kubeconfig at `/etc/rancher/k3s/k3s.yaml` on the server, but the API server address is `127.0.0.1` — useless from a remote machine. SSH'd in, grabbed the file, and used `sed` to swap the address for the VPS public IP on the way out:

```bash
ssh USER@VPS_IP "sudo cat /etc/rancher/k3s/k3s.yaml" | sed 's/127.0.0.1/VPS_IP/g' > ~/.kube/k3s-prod.yaml
export KUBECONFIG=~/.kube/k3s-prod.yaml
```

After that, every `kubectl` and `helm` command runs locally but talks to the cluster over the network. Nothing gets installed on the laptop.

## installing kube-prometheus-stack
Installed via Helm from the local machine — Helm reads the kubeconfig just like kubectl. Added the prometheus-community repo, then installed with a custom `monitoring/values.yaml` tuned for a 4GB single-node VPS: alertmanager disabled, reduced resource limits (Prometheus capped at 512Mi), 7d retention, 5Gi PVC, node-exporter enabled.

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install kube-prometheus-stack prometheus-community/kube-prometheus-stack --namespace monitoring --create-namespace --values monitoring/values.yaml
```

Key thing: the whole install command must be on one line. Backslash line continuations in the shell dropped the `--namespace` flag silently. Once running, confirmed the service name with `kubectl -n monitoring get svc` — it's `prometheus-operated`, which matches the backend's default `PROMETHEUS_URL`.

## hooking up the backend APIs

The Go server started with only two endpoints: `GET /health` and `GET /metrics` (Prometheus exposition). Added three new ones:

**`GET /api/v1/cluster`** — uses `client-go` with `rest.InClusterConfig()` to talk to the k8s API from inside the pod. Lists nodes (count, kubelet version → k3s version, oldest node creation time → uptime) and pods (running count, total, restart count filtered to last 24h via `LastTerminationState.Terminated.FinishedAt`). Returns JSON. Falls back to zeroed response when running outside the cluster — so local dev doesn't crash.

**`GET /api/v1/services`** — lists Deployments across all namespaces via client-go. Maps each to `{ name, namespace, image, replicas_ready, replicas_desired, status }`. Status logic: `"running"` if ready == desired, `"pending"` if ready < desired, `"error"` if desired == 0.

**`GET /api/v1/resources`** — originally `/proc`, then rewritten to Prometheus (see below).

Added `k8s.io/client-go`, `k8s.io/api`, `k8s.io/apimachinery` to `go.mod`. The client is initialized once in `server.New()` and stored on the `Server` struct as `*kubernetes.Clientset` — nil when outside a cluster. Every handler does a nil check before using it.

**CORS** — updated `corsMiddleware` to also handle `OPTIONS` preflight requests (browsers send these before cross-origin POSTs/GETs with custom headers). Without it, the React app would be blocked by CORS before any data fetched. Also added `http://localhost:5173` to the default allowed origins so the Vite dev server works out of the box.

**IngressRoute** — added a second Traefik route matching `PathPrefix(/api/)` so the new endpoints are publicly reachable at `api.lcpatterns.dev`. Previously only `/health` was exposed.

**React side (`src/api.js`)** — four fetch helpers, each just a `fetch().then(r => r.json())`. `App.jsx` runs `Promise.allSettled([fetchHealth(), fetchCluster(), fetchServices(), fetchResources()])` on a 5s interval. `allSettled` is important — if one endpoint is down, the others still update. Each result is checked for `status === 'fulfilled'` before updating state.

## /proc vs container namespace realization
Built a full working `/proc` implementation: sampled CPU stats twice with 500ms delay to compute idle delta, read `MemAvailable`/`MemTotal` for memory, aggregated `io_ticks` across block devices, summed rx/tx bytes across non-loopback interfaces. Clean code, worked locally.

Then realized the blocker: Linux containers have their own process namespace. When you `cat /proc/stat` inside a k8s pod, you're seeing **that pod's CPU time**, not the node's. For actual node-level metrics you need either the Metrics API, node-exporter scraping, or `hostPID: true` (which breaks isolation).

Since kube-prometheus-stack was already deploying node-exporter to every node, the cleanest path was to **query Prometheus directly**. Deleted the `/proc` parsing code entirely and replaced it with 5 PromQL queries hitting the Prometheus HTTP API at `prometheus-operated.monitoring.svc.cluster.local:9090`. One request gets us aggregated node CPU, memory, disk I/O, and network—no filesystem tricks needed.

## questions:
Why not just use the Metrics API instead of Prometheus?
>Metrics API gives pod-level resource requests/usage, not node-level observability. We needed CPU, memory, I/O, network across the whole node, which is a Prometheus job.

How does the CRT grain filter work in the data URI?
>SVG `feTurbulence` with a low frequency creates noise, then we tile it at 2×2 or 4×4 for a retro scanline feel. Base64-encoded in a data URI so it's one payload, no extra fetch.

Why migrate to React at all if it's just a dashboard?
>Once we started polling the backend every 2–3 seconds, vanilla JS state management became a mess. React's re-render cycle made the code predictable and testable.

## tradeoffs, decisions why:
Prometheus querying over /proc parsing
>Container namespaces break `/proc` for node metrics. Prometheus was already there via kube-prometheus-stack, so querying it was simpler than adding rbac or `hostPID` workarounds.

Plain HTML → React build step
>Added Vite overhead but gained predictable state, component reusability, and easier polling logic. For a metric dashboard, the win justified the complexity.

VITE_API_URL as env var, not in repo
>Environment-specific endpoint shouldn't be version-controlled. Vercel's env var injection is the standard pattern and keeps deployments flexible.

## notes
**container namespace**
>Linux containers see their own `/proc`, not the host's. For node-level metrics, need Prometheus, Metrics API, or `hostPID: true`.

**stroke-dashoffset gauge animation**
>SVG circle stroke-dasharray = circumference (2π×radius). Offset ranges from 0 to circumference to show fill %. Looks like a classic analog gauge.

**Bebas Neue + Plex Mono**
>Geometric sans for headers (command center feel), monospace for data (readability, tech aesthetic).

**kube-prometheus-stack includes node-exporter**
>Scrapes `/proc` on the node itself, exposes metrics at `http://node:9100/metrics`. That's what Prometheus scrapes, so we query Prometheus instead of `/proc` in-pod.

## commands
**kubectl -n default get replicasets**
>List all ReplicaSets in default namespace; shows desired/current/ready counts. If new RS is 0/0/0, it never scheduled.

**kubectl rollout status deployment/k8s-platform --timeout=120s**
>Wait for deployment to roll out; exits 0 if ready before timeout, non-zero otherwise. This is what hangs the CI step.

**curl http://prometheus-operated.monitoring.svc.cluster.local:9090/api/v1/query?query=node_cpu_seconds_total**
>Query Prometheus HTTP API from inside the cluster. `prometheus-operated` is the Headless Service created by kube-prometheus-stack.
